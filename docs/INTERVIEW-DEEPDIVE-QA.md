### 一、对话记忆与 FileBasedChatMemory

#### Q1：Spring AI 不是已经有对话记忆了吗？你为什么还要自己实现 FileBasedChatMemory？

**A：**  
Spring AI 默认确实提供了对话记忆能力，比如 `MessageWindowChatMemory` 配合 `MessageChatMemoryAdvisor`，可以把近期多轮对话消息自动注入到 prompt 里。但这些默认实现通常是基于 **内存存储** 的，比如 `InMemoryChatMemoryRepository`，一旦服务重启、实例重建或扩缩容，内存里的对话历史就会丢失。

在真实业务里，我们更希望用户下次再来时还能延续上一次的对话，所以我实现了自定义的 `FileBasedChatMemory`，同样实现 Spring AI 的 `ChatMemory` 接口，但底层将 `List<Message>` 通过 Kryo 序列化到 `.kryo` 文件中。这样在服务重启后，也可以通过会话 ID 把历史对话从文件中读回来，实现 **跨重启的多轮对话持久化**。

---

#### Q2：为什么不用数据库或者 Redis，而是先做成文件存储？

**A：**  
主要有两个考虑：

- **工程演进节奏**：一开始项目是个人学习和求职作品，更关注“架构思路是否正确”和“是否具备工程化扩展能力”，文件存储实现成本更低、依赖更少、部署简单，有利于快速验证方案。
- **接口设计前置**：我通过 `ChatMemory` 抽象 + Kryo 序列化，把对话对象统一成 `byte[]`，写入文件只是一个实现细节。后续如果要接入 Redis，只需要把 “写文件” 替换成 “写 Redis”，接口层几乎不用改。这种做法在代码层面已经为将来接入 Redis 或其他持久化存储打好了基础。

所以可以理解为：**当前用文件是权衡开发成本的选择，但在接口和序列化层面已经为未来接入 Redis/数据库做好了预留。**

---

#### Q3：你为什么选择 Kryo，而不是 JSON 或 ProtoBuf？

**A：**  
Kryo 相对 JSON/ProtoBuf 有几个特点比较适合这个场景：

- **性能和体积**：Kryo 是二进制序列化，序列化/反序列化更快、体积更小，适合频繁读写对话历史的场景；
- **对复杂对象支持好**：Spring AI 的 `Message` 结构并不是简单的 POJO，里面可能有层级结构和多种实现，用 JSON 序列化时容易遇到类型信息丢失或需要写较多自定义配置；Kryo 在 Java 对象图序列化这块比较成熟。
- **天然适配 Redis 等存储**：Kryo 输出的是 `byte[]`，既可以写文件，也可以作为 Redis 的 value 存储，后续演进很方便。

JSON 当然也可以用，但它更适合“需要人可读”“跨语言交互”的场景；在这个内部持久化场景里，Kryo 的综合性价比更高。

---

#### Q4：你刚才提到 Redis 不能存自然语言，这个说法准确吗？

**A：**  
严格来说不准确。Redis 的 string 类型本身可以存任意 UTF-8 文本，自然语言完全没问题。真正不能直接放进 Redis 的是“**Java 对象本身**”，必须经过某种序列化之后才能存。

我这里更准确的意思是：**Redis 不会理解 Java 对象结构**，所以需要先把像 `List<Message>` 这样的对象通过 Kryo 序列化成 `byte[]`，再作为 Redis 的 value 存入。Kryo 在这里的价值是：统一了“对象 → 二进制”的过程，既能写文件，又能写 Redis。

### 二、RAG 与 PGvector

#### Q5：为什么选择 PGvector 作为向量存储，而不是 Elasticsearch、Milvus 等？

**A：**  
PGvector 的优势在于：

- 与 Postgres 深度集成，部署和维护成本低，很适合个人项目或中小规模应用；
- 对我当前项目的规模（旅行知识库）来说，PGvector 的性能完全够用；
- Spring AI 对 PGvector 这类向量存储有比较成熟的集成，接入成本更低。

如果是 TB 级别的向量库、对吞吐有极致要求，Milvus、Elasticsearch 等会更适合。但在这个项目中，我更看重的是“**易用性 + 足够的性能 + 生态兼容**”，所以选了 PGvector。

---

#### Q6：RAG 检索里，你是怎么权衡 TopK、Filter 和相似度阈值的？

**A：**  
我把 RAG 的控制分成三层：

1. **Filter（业务约束）**：先用 metadata 做过滤，比如城市、主题、时间范围。这一步是为了保证“**业务上对得上**”，比如用户问上海，尽量只在上海相关的 chunk 里检索。
2. **TopK（候选数）**：在过滤后的候选集中，按向量相似度取前 K 条。K 不能太大——太大容易把很多边缘内容塞进上下文，干扰模型；也不能太小——太小可能漏掉有用信息。
3. **相似度阈值（质量闸门）**：对 TopK 结果再做一次过滤，把相似度太低的结果剔除。这里我不会强行追求“返回固定条数”，宁可少给，也不把噪音塞进 prompt。

这个三层组合的效果是：**Filter 负责正确性，TopK 负责召回覆盖，阈值负责质量**。实际调优时，我会先定 Filter 规则，再通过测试和日志观察，逐步调 K 和阈值。

---

#### Q7：相似度阈值你是怎么选的？会不会说反「越大越相似 / 越小越相似」？

**A：**  
这确实是一个容易踩坑的点。不同库对“相似度/距离”的定义不一样：

- 有的返回的是“**相似度**”，值越大越相似；
- 有的返回的是“**距离**”，值越小越相似。

所以我的做法是：

- 在工程实现上，先搞清楚 PGvector 配置的是哪一种度量（例如 cosine distance 还是 inner product），以及 Spring AI 对这个字段的封装；
- 然后在代码和配置里统一用“score”或“distance”，并封装一层含义清晰的方法，比如 `isAcceptable(score)`，内部根据具体度量来判断阈值；
- 在对外口述时，我会避免说“越大越相似/越小越相似”的细节，而是说“根据向量库的度量方式设置阈值来过滤低质量召回”。

这样既能保证实现不出错，又不会在面试时被小细节卡住。

### 三、ReAct Agent 与多步执行

#### Q8：ReAct Agent 的 step 循环具体是怎么设计的？如何保证不会无限循环？

**A：**  
我这边的设计大致是：

- `run()` 方法内部有一个 for 循环，从 1 执行到 `maxSteps`；
- 每一步调用抽象的 `step()` 方法，由子类实现具体逻辑：构造 prompt、调用 LLM、解析输出、决定是否调用工具、更新状态；
- 每步执行完之后，根据当前 `AgentState` 判断是否需要继续：
  - 如果变成 `FINISHED` 或 `ERROR`，立即退出循环；
  - 否则继续下一步。

同时，我设置了一个硬性的 `maxSteps` 上限，即使模型一直想“再试一步”，超过上限也会强制退出，并把状态设为 FINISHED 或 ERROR。这相当于给智能体套了一个“安全护栏”，既防止逻辑上的死循环，也防止成本失控。

---

#### Q9：为什么要把 ReActAgent、ToolCallAgent 和 SyManus 分成三层？不能写成一个大类吗？

**A：**  
从工程角度看，我希望：

- **ReActAgent** 专注于“多步执行 + 状态管理”这个通用能力；
- **ToolCallAgent** 在此基础上，扩展“识别模型的工具调用请求并执行工具”的能力；
- **SyManus** 则是一个面向具体业务的组合体，配置系统提示词、可用工具集等。

这样分层的好处是：

- 框架层（ReActAgent）很稳定，可以被多个场景复用；
- 工具调用逻辑集中在 ToolCallAgent，便于统一处理协议和错误；
- 新增不同场景的 Agent（比如只用搜索的 Agent、只用内部 API 的 Agent），只需要在最上层替换 prompt 和工具组合，无需改底层循环逻辑。

如果一开始就写成一个大类，短期看实现简单，但后期扩展和维护成本会非常高。

### 四、工具框架与 MCP

#### Q10：你说工具是通过 Spring 配置化注册的，这样做的好处是什么？

**A：**  
主要有三点：

1. **解耦**：工具本身是 Spring Bean，通过 `ToolRegistration` 集中注册。Agent 只依赖抽象接口，不需要关心每个工具如何实例化、如何注入配置。
2. **可测试**：工具可以单独注入到测试上下文中，用 Mock 替换外部依赖，方便做单测和集成测试。
3. **可治理**：未来如果要对部分工具做权限控制、限流、熔断或者打审计日志，有一个统一的注册中心会更方便扩展。

简单说，就是把“工具”从“写死在 Agent 里的一段代码”提升成“可配置、可治理的资源”。

---

#### Q11：为什么要把图片搜索做成独立的 MCP 服务，而不是直接在主应用里集成 Pexels API？

**A：**  
从架构上看，图片搜索是一个典型的“边界外能力”：

- 它依赖外部 API，有自己的网络、鉴权、限流等关注点；
- 与主应用的核心逻辑（旅行规划、RAG、对话）耦合度相对较低。

把它做成独立的 MCP 服务，有几个好处：

- **解耦发布和故障域**：图片服务出问题时，不会直接拖垮主应用；可以独立升级、回滚；
- **生态扩展**：MCP 是标准协议，未来如果要接更多外部能力（地图、企业内部系统），沿用同样的方式接入即可；
- **多语言/多团队协作**：即便别的团队用 Node.js 或其他语言实现 MCP Server，主应用也只需要作为 MCP Client 调用。

---

#### Q12：stdio 和 SSE 两种 MCP 模式分别适合什么场景？

**A：**  
简单来说：

- **stdio 模式**：
  - 更适合本地开发或轻量部署；
  - 主应用直接拉起 MCP 子进程，用标准输入输出通信；
  - 优点是配置简单，不需要额外开端口；
  - 缺点是进程管理、资源隔离较弱。

- **SSE 模式**：
  - 更适合正式环境或云端部署；
  - MCP Server 独立运行，主应用通过 HTTP + SSE 连接；
  - 优点是可以独立扩缩容，方便做监控、限流、熔断等；
  - 缺点是部署稍微复杂一点，需要额外服务和端口。

我在项目里通过不同 Profile 支持了这两种模式，方便在本地和线上切换。

### 五、测试与可观测性

#### Q13：智能体这种不确定性很强的系统，你是怎么做自动化测试的？

**A：**  
我会把“可测性”拆成几个层次：

1. **工具层单测**：对各个工具的输入输出做精确断言，外部依赖（比如 HTTP 调用）全部 Mock 掉，保证逻辑正确。
2. **场景化集成测试**：对多工具串联的典型场景（搜索 → 抓取 → 生成 PDF）写集成用例，但不会要求大模型输出的自然语言“字字一致”，而是检查：
   - 是否按预期调用了工具；
   - 是否走到 FINISHED 状态；
   - 是否生成了目标文件或结构化结果。
3. **可观测性**：通过日志 Advisor 记录请求、检索结果摘要、工具调用链、Agent 步数与状态，必要时加上简单的指标。出现问题时，可以快速定位是检索问题、工具问题，还是模型决策问题。

这样一来，即使大模型存在一定的不稳定性，整个链路依然是“**可回归、可排查**”的。

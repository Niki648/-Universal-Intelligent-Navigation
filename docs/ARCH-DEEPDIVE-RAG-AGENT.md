## RAG & Agent 架构深度解析（路线 A）

> 这份稿子偏「架构硬核」，适合系统设计 / 技术深挖场景使用。

---

### 一、RAG 架构深挖

#### 1. 整体目标

- **核心目标**：让大模型在回答用户问题时，有稳定、可控、可追溯的“外部知识支撑”，而不是完全靠自身记忆和参数。
- **设计原则**：
  - **可控性**：检索结果必须可解释、可调参（TopK、阈值、过滤条件等）。
  - **业务对齐**：不仅要语义相似，还要满足城市、主题、时间等业务约束。
  - **可扩展性**：方便后续替换 Embedding 模型、切换向量库或扩展元数据维度。

#### 2. 文档切分（chunking）与元数据设计

- **文档切分**：
  - 旅行知识库以 Markdown 文档形式存在，例如按城市、景点、玩法等维度组织。
  - 切分策略上采用「固定长度 + 适度重叠」：
    - 每个 chunk 控制在一个合理的 token 范围内（便于后续放进 prompt）。
    - 相邻 chunk 之间保留少量重叠，避免信息被切断导致语义不完整。
  - 这样处理的好处是：**单个 chunk 足够自洽**，既不会太碎，也不会太长。

- **元数据（metadata）设计**：
  - 对每个 chunk，我会附加一组结构化元数据，例如：
    - `city`：上海 / 北京 / 东京……
    - `category`：美食 / 景点 / 交通 / 住宿……
    - `duration_tag`：周末游 / 3-5 天 / 7 天以上……
    - `source`：来源文档名或知识库分类。
  - 这些元数据在向量入库时一并写入，为后续 Filter 检索提供维度支持。

#### 3. 向量化与 PGvector 选型

- **Embedding 模型**：使用 Spring AI 配置的 Embedding 模型，将每个 chunk 编码为高维向量。
- **向量库选型：PGvector**：
  - 与 Postgres 深度集成，部署和维护成本低，易于与现有数据库生态整合。
  - 支持多种距离度量与索引结构，其中我在本项目里使用 **HNSW + 余弦相似度**。
  - 对小规模到中等规模的数据集，非常适合作为 RAG 的向量存储。

#### 4. 索引与相似度：HNSW + 余弦

- **HNSW（Hierarchical Navigable Small World）索引**：
  - 优点：适合做近似最近邻搜索，在向量规模增大时，仍然能保持较好的检索速度。
  - 对于在线请求场景，与精确暴力搜索比，延迟更低，体验更稳定。

- **余弦相似度（Cosine Similarity）**：
  - 文本 Embedding 常用度量方式之一。
  - 通常可以理解为“夹角越小越相似”，或者“相似度值越高越像”。
  - 实际工程中需要注意：有的库返回的是 **相似度**（值越大越相似），有的是 **距离**（值越小越相似），配置和阈值需要与具体实现对齐。

#### 5. 检索阶段：Filter + 相似度阈值的双闸门

- **第一道闸门：Filter 过滤**
  - 在向量检索前，先根据业务条件对候选集合进行收缩，比如：
    - 只检索某个城市 `city = 'Shanghai'`；
    - 或只检索「景点」类内容 `category = 'sightseeing'`；
    - 或只检索近几年更新的内容等。
  - 目的：**保证业务正确性**——不会在“上海 3 天游”里混入“北京 7 天游”的建议。

- **第二道闸门：相似度阈值**
  - 在拿到 TopK 候选后，根据相似度/距离再做一次过滤：
    - 相似度太低（或距离太大）的片段宁可不要，也不强行塞到上下文里。
  - 目的：**保证语义相关性**，降低模型“抓不到重点”的风险。

- **最终注入控制**：
  - 即便通过了双重过滤，我仍然会限制：
    - 最多注入 N 条文档片段；
    - 每条片段截断长度；
    - 注入格式（例如前置“来源：xxx，内容：xxx”）。
  - 这样能在 **上下文预算（token budget）** 与 **信息丰富度** 之间找到平衡。

#### 6. Advisor 封装：RetrievalAugmentationAdvisor

- 将上述流程封装成自定义的 `RetrievalAugmentationAdvisor`：
  - 它被集成到 Spring AI 的 `ChatClient` 调用链里；
  - 在模型生成回复之前，先对用户提问做一次检索，将检索结果注入到系统/用户提示词上下文中；
  - 对上层业务来说，只需要关心“有没有开启 RAG、检索用哪个知识库”，不需要关心底层细节。

- 优点：
  - **可插拔**：可以针对不同场景（旅行、百科、企业知识库）配置不同的 Advisor。
  - **可调参**：TopK、Filter 条件、阈值都可以在配置层调整，不影响 Agent 主流程。

### 二、ReAct Agent 架构深挖

#### 1. 设计目标

- 让智能体具备：
  - **分步推理与执行**能力（不是一问一答，而是多步计划）；
  - **多工具编排**能力（搜索 → 抓取 → 下载资源 → 生成 PDF 等）；
  - **可控的终止条件与状态管理**，避免陷入死循环。

#### 2. 分层结构：ReActAgent → ToolCallAgent → SyManus

- **ReActAgent（抽象基类）**：
  - 管理 Agent 的核心通用能力：
    - 状态机：`AgentState`（IDLE/RUNNING/FINISHED/ERROR）；
    - `maxSteps` 最大步数与 `currentStep` 当前步数；
    - `messageList` 对话/思考/工具调用的消息上下文；
    - 执行循环 `run()` / `runAsync()`，内部调用抽象方法 `step()`。

- **ToolCallAgent（工具调用 Agent）**：
  - 在 ReActAgent 的基础上，加入对「工具调用协议」的支持：
    - 能从大模型输出中识别工具调用请求（tool call）；
    - 执行对应的工具（通过工具注册中心）；
    - 把工具执行结果包装成 `ToolResponseMessage` 写回消息上下文。

- **SyManus（场景化 Agent）**：
  - 面向具体业务场景（如“万能智能助理”）的配置型 Agent：
    - 定义专属的系统提示词（system prompt）；
    - 配置能够使用的工具集合（搜索、图片、抓取、PDF 等）；
    - 可根据场景调整 maxSteps、终止策略、输出格式等。

#### 3. 执行循环与状态机

- **执行流程简述**：
  1. 校验当前状态（必须是 `IDLE`），并初始化 `messageList`（含 system prompt 与历史对话）。
  2. 切换状态为 `RUNNING`，开始按步执行循环：
     - 每一步调用 `step()` 让模型决策下一步。
     - `step()` 内部包含：构造 prompt → 调用 LLM → 解析输出 → 可能触发工具调用。
  3. 根据本步结果决定：
     - 若任务完成：设置状态为 `FINISHED`，退出循环；
     - 若异常或不可恢复错误：设置为 `ERROR`，退出循环；
     - 若未完成但未超步数：继续下一步。
  4. 达到 `maxSteps` 仍未完成，则强制结束，防止死循环。

- **状态机的价值**：
  - **防止非法操作**：例如在 RUNNING 状态重复调用 `run()`；
  - **便于观察与调试**：日志中可以清晰看到 state 的变化；
  - **为上层控制留接口**：例如前端/调用方根据 state 决定 UI 展示与错误提示。

#### 4. 消息上下文管理与 token 控制

- `messageList` 中包含：
  - 系统提示词（system）；
  - 用户消息（user）；
  - 模型回复（assistant）；
  - 工具调用与工具响应（tool call / tool response）；
  - 以及必要的中间结果。

- **历史裁剪策略**：
  - 读取历史消息时只加载最近 N 条（例如 20 条）；
  - 保存结果时也控制最大保存条数（例如 30 条）；
  - 避免上下文无限增长导致：
    - token 成本不可控；
    - 单次请求超出模型上下文长度上限。

- **对用户可见性控制**：
  - 有些中间状态（例如“内部思考”、“工具调用细节”）不直接推给前端；
  - 而是通过日志和可观测指标记录，既便于排查，又避免干扰用户体验。

#### 5. 工具调用与错误处理

- **工具调用流程**：
  1. 模型输出包含工具调用决策；
  2. Agent 解析出要调用的工具名及参数；
  3. 通过工具注册中心找到对应的 ToolCallback；
  4. 执行工具并捕获结果或异常；
  5. 生成 `ToolResponseMessage` 加入 `messageList`，作为下一步 LLM 输入的一部分。

- **错误处理策略**：
  - 对于可恢复的错误（例如网络闪断、暂时不可用）可以重试或引导模型调整策略；
  - 对于不可恢复的错误（例如参数严重不合法）则直接记录到日志，设置状态为 `ERROR`，并给用户一个友好的失败提示。

---

### 三、小结：RAG + ReAct 架构的协同

- RAG 负责的是「**把外部知识以可控方式喂给模型**」，解决“知道什么”的问题；
- ReAct Agent 负责的是「**让模型能够分步思考并合理使用工具**」，解决“怎么做”的问题。

两者结合后，系统既能基于可靠的知识库回答问题，又能利用外部工具链完成复杂任务，整体表现更接近一个“真正可落地的智能体”，而不是简单的聊天机器人 demo。
